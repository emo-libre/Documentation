# `Secret` Request Header

## Overview

Every HTTPS request the EMO device sends to Living.ai servers includes a custom header:

```
Secret: CTV26NwqYh_PaQaLJPjIkw
Secret: rbNzkE3o6EeLECzRUKLopA
Secret: 4XQNmt18dOR1uB7ug8uT3Q
```

The value is 22 characters of Base64url (no padding), which encodes 16 bytes. This document explains exactly how it is generated, based on static analysis of the ESP32 firmware (`alexa.bin`, version 3.1.0).

---

## Reverse Engineering

### Location in firmware

The Secret is generated by function `FUN_40120b7c` in the ESP32 firmware. It is called immediately before each HTTP POST request is assembled.

### Algorithm — step by step

**Step 1 — Get Unix timestamp**

If the Unix timestamp is less than 0x5f844acb (decimal 1602504395, roughly October 2020), the firmware substitutes a hardcoded fallback value of 1000000000 instead. This guard likely exists to handle clock failures or an uninitialized RTC.

**Step 2 — Build the 16-byte message**

The format string (found at address `0x3f4114e4`) concatenates the decimal timestamp with a literal suffix. For any current Unix timestamp (10 digits), the result is exactly 16 bytes — one AES block.

**Step 3 — AES-128-ECB encrypt**

Despite the code using a CMAC-structured context, the single-block path performs a plain AES-128-ECB encryption with no subkey derivation or chaining. The 16-byte ciphertext is the MAC output.

The AES operation is hardware-accelerated via the ESP32 AES peripheral.

**Step 4 — Base64url encode**

Standard Base64 with URL-safe substitutions and no padding, producing exactly 22 characters.

---

## Key Findings

**The Secret is not device-specific.**
No MAC address, device token, or any other per-device value is mixed into the input. Every EMO device running the same firmware version produces the identical Secret for any given second.

**The AES key is plaintext in flash.**
The AES key is stored as a regular string at firmware address `0x3f4114fe`.
